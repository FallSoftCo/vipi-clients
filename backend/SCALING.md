# Scale and drain the Vipi relay

Scale the HTTP/foreground WebSocket role that is approaching its measured limit. On one host a second copy of the immutable release can take new traffic while the first completes accepted requests. PostgreSQL holds the durable message, receipt, grant and lease state. Each API worker also opens a dedicated PostgreSQL LISTEN connection for foreground hints. Clients fetch the durable inbox on reconnect. Media workers need the same ciphertext files as well as the same database.

## Rehearse the switch on one Linux host

Use Python 3.12 with the locked backend and test dependencies, PostgreSQL 16, Nginx, iproute2 and unprivileged user/network namespaces. From the repository root, set the Python and Nginx paths to your local executables. Set the parent directory to an owned disk-backed path short enough for a PostgreSQL Unix socket.

```sh
python_bin="$PWD/backend/.venv/bin/python"
nginx_bin="$(command -v nginx)"
: "${nginx_bin:?set nginx_bin to the local Nginx executable}"
run_parent="$PWD"
run="$(mktemp -d "$run_parent/scale.XXXXXX")"
systemd-run --user --quiet --wait --pipe --collect \
  --working-directory="$PWD" -p UMask=0077 -p CPUQuota=200% \
  -p MemoryMax=1G -p MemorySwapMax=0 -p TasksMax=96 -p RuntimeMaxSec=180 \
  -E "SCALE_NGINX=$nginx_bin" \
  unshare -Un --map-current-user --keep-caps sh -ec 'ip link set lo up; exec "$@"' qa \
  "$python_bin" scripts/test-postgres.py --run-directory "$run/pg" \
  --basetemp="$run/pg/pytest" tests/test_scale_drain.py
```

Check that the test passed and that `pg/result.json` records `private_cluster_removed: true`. The process identities, upstream ports, saturated database pool counts, ciphertext byte count and durable final counts are in `pg/pytest/test_scale_drain0/scale-drain.json`. A skipped test supplies no drain evidence. The runner creates a new cluster, and the network namespace exposes loopback. The QA-only upstream-selection header makes direction deterministic. The ordinary path load-balances across both entries before the switch. Keep that header out of deployed routing.

In the November 27 run, both original WebSocket and HTTP work survived one Nginx reload. A 196,636-byte AES-GCM upload finished on the removed upstream. The recipient downloaded and decrypted it through the survivor after the first API process exited. An authenticated recipient moved its WebSocket from A to B and fetched the previously accepted text. A receipt posted through the survivor reached the sender's original socket. Two messages ended delivered, both stored envelope payloads were cleared, one finalized object and grant remained, and the durable push generation reached two. [Qualification receipt](qa/scale-drain-20261127.json)

An earlier run on the same private source found that retrying an accepted ID returned the original message but advanced the outbox again. The HTTP handler enqueued on every returned `accepted` state. The fix enqueues inside the new-envelope branch of the existing transaction, after attachment grants succeed. The recipient/user locks serialize competing admissions. Accepted replays return earlier and conflicting reuse raises 409. Silent chat envelopes keep their prior push policy. Group membership, fan-out and its transaction/savepoint continue to govern group acceptance.

This exercise uses synthetic identity and envelope credentials, real PostgreSQL and encrypted file bytes. It measured route convergence and durable effects at bounded concurrency. The fixture runs the current full API in two independent processes with a disposable schema created from its ORM models. It uses development settings and probes readiness through the proxy. The separate package rehearsals migrate fresh clusters through the three release heads and exercise role-specific readiness and permissions. The deployed inbox/profile method restrictions, general role and background workers require their own release contracts. The attachment key stays in the test client. Native Signal key exchange, store-installed clients, public TLS/WAN behavior, external push delivery and physical host loss are outside this run.

## Add capacity to a serving role

1. **Measure the bottleneck.** Retain busy-window samples of accepts, pending fetches, receipt latency, errors, WebSocket count/reconnects, transfer slots and provider/maintenance backlog. Include each upstream's CPU, RSS, FDs and worker identities, PG client connections and lock waits, and media volume bytes/inodes. Choose the role that owns the slow path. At the recorded schema-01 deployment, inbox owned `GET /v1/messages/pending`, profile owned `GET /v1/entitlements` and `PUT /v1/me`, and General owned the remaining public methods. Read the effective config and current owner receipts before changing that map.
2. **Budget the overlap.** For each added API worker, budget its ORM pool size plus maximum overflow plus one LISTEN connection. The reviewed serving package used 3 + 2 + 1, so a two-worker unit could add 12 PG connections. The integrated source fixture used SQLAlchemy's 5 + 10 + 1 per worker. Offering 17 authenticated pending requests to each process produced 15 simultaneous ORM lock waiters per process, and all 34 requests completed after the private fixture released its lock. Reserve regular slots for all incumbent roles, scheduled work and operator access and preserve any required free-slot floor after the worst case. Account for old and new memory/CPU/task/FD limits simultaneously.
3. **Qualify a like-for-like instance.** In the private infrastructure source, pin release file hashes, exact role factory, method allowlist and feature settings, schema heads, secrets/identity custody, bounded unit settings and a free private endpoint. Give each instance its own runtime and worker-observation directory. Confirm exact DB and LISTEN routing, compatibility with stored and negotiated client formats, current health and authorization contracts. Check the role’s feature-state readiness as well as its schema version. In the separate package contract rehearsal, the inbox bridge became ineligible on populated feature state while the profile stayed healthy. The General role’s protected-only mode still handled seven paid methods. Retirement needs a fence covering every method it owns. Use the current operator access and shared-host maintenance process. [Human release procedure](../docs/HUMAN_RELEASE.md)
4. **Keep writer ownership explicit.** Replicate only the selected API role. Push dispatch, store/billing reconciliation, expiry/media cleanup, deletion and any provider-backed operations retain their established owners. Preserve original lease and operation IDs, provider references and unknown outcomes. To move a writer, first fence *new* claims on its old executor, let accepted claims settle or explicitly retain their unknown disposition, then admit the new owner. Queued durable rows can transfer in place. A timed-out provider call or expired lease alone cannot establish whether an external effect occurred.
5. **Check shared storage before enabling media on another instance.** All upload, download and cleanup paths for the same blob must see one qualified volume, marker, permissions, capacity ledger, byte/inode reserves, advisory locks, file locks, allocation, atomic rename and fsync semantics. Private writable scratch or a second locally named directory cannot serve existing accepted blobs. Include proxy request/response buffering and temporary-body locations in the privacy and capacity review. A second physical host requires its own verified shared storage and private PostgreSQL transport; the existing local Unix socket and native ext4 directory only span processes on their host.
6. **Add the member and observe traffic.** Review the exact upstream change and compatible fallback with the affected owners. Start the approved private unit, verify its PID/start identity, readiness and original worker set, then compare the old/new full Nginx configurations and syntax-test the candidate. Apply one reviewed graceful reload. Record the original master/workers, accepting listener FDs, backend identities and actual per-upstream responses. Confirm the intended methods reach both eligible members and all other method owners still match. Preserve original accepted streams. The fixture disables automatic upstream retries. Production must never automatically replay an ambiguous mutation with an unknown external effect.

## Remove a member or revert a traffic change

1. Fence fresh ingress to that member on every relevant method and path, including direct/private callers. Keep its unit and storage available. After the graceful reload verify the same Nginx master, fresh worker generation, and the release of **all original accepting listener FDs** on the relevant addresses. A fresh response from the new upstream can arrive while an old worker still accepts connections.
2. Verify new requests and WebSocket reconnects reach the survivor. Keep the original backend alive for upgraded sockets, keepalive requests already accepted, streaming upload/download bodies, in-progress receipts and idempotent result reads. Check the original per-worker authenticated work counters where available, existing sockets and worker identities. Correlate DB transactions, media partials/reservations and any provider/lease references with their accepted work. A zero PG lock count or empty HTTP sample alone cannot establish a drain. If an old socket outlives the window, record that traffic has switched and leave retirement pending.
3. When all old admissions are fenced, the original workers have drained, and each outstanding effect has an owner, use the current approved procedure to retire **only** the identified unit. Verify original cohort identity immediately before stopping it. Check surviving readiness, pending fetch, receipt propagation, media/object counts, resource headroom and alerts. Record the exact configuration digests, observed identities, timings, outstanding exceptions and final effect counts.
4. If the switch stalls or a reload/stop response is lost, inspect the original command receipt, on-disk config, master/worker identities, listeners and observed upstreams. Route new traffic back only to a healthy generation compatible with the **current** schema and every already-admitted format. Keep both generations available for accepted work and preserve operation IDs. Schema rollback, stale DB restoration, a force-stop or reissuing a provider request can lose or duplicate work.

The earlier dedicated host study held 4,096 active sockets at 30 sends/s for 150 seconds and 8,192 idle sockets for 100 seconds in its measured configuration. The later media-ingress run covered two Uvicorn workers sharing one POSIX volume behind private TLS. Neither study measured this build at those limits. Use the current workload, admission settings, physical storage and a separate client with enough headroom for the next throughput or cross-host qualification.
