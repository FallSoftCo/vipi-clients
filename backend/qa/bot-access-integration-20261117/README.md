# Bot access integration qualification

The incident exposed two separate gates: a complimentary grant pinned to a different shared identity did not cover the owner's actual profile, and a replaced device could read account allowance while its send was correctly rejected. The production entitlement correction used the existing exact-profile UUID allowlist; these tests introduce no service, billing, identity or client behavior change.

`tests/test_bot_access_integration.py` exercises real ASGI routes, database records, subscription selection and BotGateway with synthetic verified principals and an in-memory provider transport:

- A grant for another shared identity does not cover the actual profile or a legacy identity with the same raw subject suffix. Before correction the actual profile receives Base's cardless trial, `available=false`, and HTTP402 `bot_subscription_required` on send, without a reservation/provider call. Adding only its exact profile UUID preserves its UUID, trial, subject, device and the other grant; Base/Bot become complimentary without creating store entitlements.
- Account-level allowance can remain `available=true` for a replaced device. Sends from revoked, foreign, missing or wrong-secret devices receive HTTP401 `device_revoked`; malformed secret input receives HTTP401 `invalid_device_credential`. None reserves quota or reaches the provider. The authorized device succeeds, duplicate request IDs are not replayed, and exhaustion returns HTTP429 `monthly_allowance_reached` with `Retry-After: 60`.
- An otherwise valid session with an older authentication time can use its registered device and send. Re-registration still requires recent authentication. This prevents treating the registration freshness guard alone as proof of a cold-start failure; it does not qualify native refresh/storage behavior.
- A complimentary grant does not bypass the profile's authentication-time floor, authentication itself, or provider consent. Rejected requests create no reservation/provider call.
- Provider timeout returns only HTTP503 `bot_reply_unconfirmed`, retains uncertain quota and prevents replay. A definite provider rejection returns HTTP503 `bot_unavailable`, records zero spend and restores quota; the same request ID still cannot be reused. Provider exception/response detail is not exposed.

The final local run passed the six new parameter-expanded cases plus the existing reviewer-access and Bot suites (26 total). The first new run exposed an incorrect test expectation: an invalid-format synthetic secret is rejected as `invalid_device_credential`, rather than `device_revoked`. The test now separately covers both input shapes; production logic was unchanged.

The live read-only followup used current production Settings in a fresh service-user process, PostgreSQL transactions forced read-only, and only the exact owner-confirmed profile. It confirmed active complimentary Base/Bot and 150 available replies, matching live API environment, unchanged profile/device/source/schema and preserved prior grants/shared services. It made no sign-in, provider request or Bot send. Private binding and full incident receipts remain outside the repository.

Boundaries: local tests use SQLite, an injected principal verifier and mocked provider I/O. They do not qualify PostgreSQL lock concurrency, real WorkOS refresh/callbacks, native stored-device selection, composer/keyboard interaction, live provider delivery, store offers or purchases. JWT/issuer, deletion/linking and provider cryptography have separate suites; no new production fix is implied by this test-only change.
