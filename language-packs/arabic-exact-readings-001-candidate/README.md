# Arabic exact-headword reading candidate

Inactive research asset, not a bundled runtime path or a generated-translation approval. `build.py --output NEW_DIRECTORY` verifies and reads the already-retained `data/lexical/d-ar.sqlite.zlib` and catalog; it never downloads source data. It copies a supplied Latin reading only for a single exact Arabic canonical surface when every exact competing native surface, lexeme, retained sense and qualifier has one matching nonempty Latin reading. Unsafe/noncanonical forms, conflicts, missing readings and blocked guards abstain. It never derives a reading from a lemma for an inflected form or generates vowels. Exact string lookup must not normalize an unknown query into a different surface.

The generated SQLite contains provenance for each included reading; the output also retains the full upstream attribution. Its Wiktionary/Kaikki data is CC BY-SA 4.0; see `data/lexical/ATTRIBUTION.txt`. `verify.py NEW_DIRECTORY` checks every generated row against the exact pinned source, plus generic database integrity and representative edge cases. It does not establish phonetic accuracy, contextual translation meaning, speed, licensing suitability for a store release or native UI behavior.

The first reproducible candidate and manifest reside at `investigations/vipi-resume-20261116-r01/arabic-exact-reading-candidate-r01` under the Development root. Compressed SHA-256 is `b2c539dc86e85b2706b045cb7efb0f8279d39a8f10322c90732ff5fb17880cc4`; 5,867 exact written surfaces are represented. These are data rows, not coverage or accuracy claims. Arabic `كوب` has the supplied reading `kūb`; `ضع` and `بالوعة` deliberately abstain under this policy. Native qualification and any activation are separate decisions.
