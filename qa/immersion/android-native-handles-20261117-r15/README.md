# Android native selection-handle qualification

The installed r13 app correctly delayed translation while dragging a native handle, but never translated the final selected phrase after release. Repeated floating ActionMode MOVE notifications reset the dirty selection flag. StableImmersionText now begins each gesture once, retains changes across MOVE, clears queued delivery on cancellation, and clears pending work on detach. No controller, core, private-field/reflection or production window-enumeration change. Minimum supported Android API remains 28; the existing public ActionMode hook is unchanged.

The new focused instrumentation uses actual touchscreen DOWN/MOVE/UP input, real TextView long press and public WindowInspector bounds for the framework's external selection handle PopupWindows. It never calls selectTextFromMenu or sets the selection programmatically. The provider is an intentionally delayed lifecycle fixture and forbids downloads. This does not qualify translation accuracy or audio quality.

Baseline r14: long press selected [4,10] and translated once after release. A native handle drag changed the selection to [4,15], held provider count at one during dragging, but produced no final request after UP. The failing report and screenshot are retained.

Passing r15/run003: initial long press produced one request after release; handle drag extended [4,10] to [4,15] without translation during dragging; exactly one final-context request followed release (two provider calls total). Both requests preserved the full enclosing source sentence. Native Copy returned exactly “marmot hums” and cancelled the pending lookup. The test passed in 9.372 seconds with only 147,456 bytes runner growth; minimum free was 5,288,632,320 bytes.

The same r14 test APK was used before and after the production fix. Final app/test hashes are pinned in installed-final-hashes.json. The focused test-only build and one normal guarded app-only package passed; no whole suite or model download was run. Original QA accounts, app/model data, production package/signing and the user's phone were untouched.

Run002 is a non-result: the inherited 20 MiB host runner growth limit stopped the app during startup after about 60 MB emulator storage growth. The resulting “Process crashed” instrumentation message reflects that deliberate host force-stop, not an established product crash. That run is retained separately. Run003 used a freshly admitted bounded 100 MiB allowance and completed with negligible additional growth. All observed free-space levels remained above the exact 4,504,682,496-byte floor. The first test-build script's reserve-term substitution mistake is transparently retained with its capacity audit; its independently enforced 100 MiB growth limit still guaranteed more than the required reserve.

To admit the normal app package, 655 owned generated files were proved byte-identical to current source/staging files and replaced with verified symlinks, freeing 663,019,520 bytes. Original inputs remained unchanged. APK asset plaintext hashes were checked before retiring closed compressed-cache intermediates; final APKs and receipts remain.
