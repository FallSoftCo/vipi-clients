Android evidence is meaningful but bounded. OpenNLP PR #892 reports a POSTagger failure caused by unsupported XML secure-processing configuration and a tested fix. Subsequent OPENNLP-1835 records additional XML-option handling fixed in **2.5.10**. GrapheneOS SpeechServices currently pins 2.5.10; its Android project uses Java 17 and optimized releases, but minSdk **36**, so it does not qualify Vipi's API-28 floor. [PR #892](https://github.com/apache/opennlp/pull/892), [OPENNLP-1835](https://issues.apache.org/jira/browse/OPENNLP-1835), [downstream version catalog](https://github.com/GrapheneOS/SpeechServices/blob/main/gradle/libs.versions.toml), [downstream Android build](https://github.com/GrapheneOS/SpeechServices/blob/main/app/build.gradle.kts).

Do not automatically substitute the newest runtime. OPENNLP-1959 is currently unresolved and lists 2.5.11/2.5.12 and 3.0.0-M5/M6 as affected: a static `ObjectInputFilter` reference is unavailable on Android. The report establishes an R8 failure against API 36, with 2.5.10 passing that build check; its predicted ART model-loading failure was explicitly not device-tested. Fix-version labels 2.5.13/3.0.0 are not proof of a released fix. Inspected 2.5.10 `BaseModel.java` contains no `ObjectInputFilter` reference and `XmlUtil.java` handles unsupported parser options. These findings support a qualification candidate, not blanket Android compatibility. [OPENNLP-1959](https://issues.apache.org/jira/browse/OPENNLP-1959), [2.5.10 source](https://github.com/apache/opennlp/tree/opennlp-2.5.10/opennlp-tools/src/main/java/opennlp/tools/util).

NER remains a separate gap. The current signed OpenNLP UD model collection supplies POS/tokenization/sentence/lemma models, not entity models. `PROPN` is useful evidence for a conservative proper-name guard, but is not person/organization/location recognition and cannot promise protection of conversational names such as Flash. OpenNLP's maintained `NameFinderME` supports NER, and the historical official 1.5 model page lists `en-ner-person.bin`, `en-ner-organization.bin`, and `en-ner-location.bin`; the current Apache page declares those legacy models compatible with 2.5.12 at toolkit level. This does not overcome 2.5.12's Android issue. Exact legacy model byte hashes, model-specific license/provenance, and Android behavior were not established here, so they are **not proposed for acquisition yet**. Do not silently label their age or toolkit-format compatibility as semantic qualification. [Current models](https://opennlp.apache.org/models.html), [legacy model inventory](https://opennlp.sourceforge.net/models-1.5/), [NameFinder API](https://opennlp.apache.org/docs/2.5.4/manual/opennlp.html#tools.namefind).

ML Kit `entity-extraction:16.0.0-beta6` has documented Android support and dynamic local models, but its supported entity inventory covers structured items such as addresses/dates/phone numbers, not general person/organization names. It is not an adequate Flash/name guard or a POS substitute; adding it would not close this gap. Its documented up-to-5.6-MB app impact is not an exact model size, and its proprietary SDK/model terms must not be confused with the Apache license on documentation code examples. [Android API](https://developers.google.com/ml-kit/language/entity-extraction/android), [supported entity types](https://developers.google.com/ml-kit/language/entity-extraction).

For the later bounded probe, load fixed local model assets via InputStreams, run sentence/token/POS annotation, and emit original UTF-16 token ranges, raw tag names, optional raw scores, and exact implementation/model identities for all 116 sources. Verify that each token equals its original substring, including contractions, punctuation, emoji and surrogate pairs. Derive a common coarse POS mapping only after preserving raw tagsets; do not assume UD coarse tags supply infinitive morphology, dependency roles, idiom membership, or lexical sense. Keep all source text in local inference. Test release-R8 model loading, cold/warm latency, peak heap, determinism and offline behavior on Vipi's actual Android path and API floor separately from linguistic judgments. Those checks have not run.

POS confidence is not calibrated lexical-sense confidence. A source VERB tag can reject a noun-only `visit` candidate, but does not choose between same-POS senses, guarantee correct target inflection, or resolve `too`, country music, or idioms. Contextual sense selection, entity/idiom abstention, and decision thresholds remain separate mechanisms with heldout conversation validation. Existing request-bound `SourceLookupEvidence` enforces approvals/masks; it does not perform these new inferences. The reused 116 sources are diagnostic comparison inputs, not independent population accuracy evidence or new training labels.
